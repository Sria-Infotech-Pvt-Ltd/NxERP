# Spike: login federation on the pinned Frappe v16.53.0 (Phase 6A)

Question: can a person who signs in at the identity site (`id`) be accepted by an app site (`hd`) with no second password, using only what Frappe v16.53.0
ships, and what exactly happens at the edges? **Answer: yes, with userinfo only.** Findings only; no product code.

## How it was run (FACT)

Date 2026-11-19. Two throwaway stacks from Phase 5 (`nxerp-id` identity, `nxerp-hd` app; image `nxerp:0.0.1-8a4910610a5b-dirty`, Frappe 16.53.0, fake data,
never a restored production copy), reached through the edge. Because the stacks call each other by public name, `edge-gen.sh` now gives the edge the host
names of every stack as network aliases on each stack's network (a stack backend can call `http://id.example.test:8080` without hairpin routing). Site `host_name`
was set to `http://<host>:8080` on both sites for the rehearsal (production uses https). Driver: `scripts/spike_federation_flow.py` (setup through `bench execute` as
Administrator, the browser side as HTTP with one cookie jar per site, redirects followed by hand). It prints statuses, names and key NAMES only: no secret,
token, cookie value or password. Re-run it: `python scripts/spike_federation_flow.py` (it cleans up its fake users, OAuth Client and Social Login Key first).

## What this means for the design (JUDGMENT)

1. **GO.** The userinfo-only flow works on the pinned Frappe with no change to Frappe.
2. **Two gates, both server side.** (i) Identity site: OAuth Client `allowed_roles` = the app's `NXERP Access: <app>` role, so a person without the grant is refused before reaching the app. (ii) App site: the user must exist, be enabled and (for access to anything) hold the app's access role, which provisioning sets; Sign ups stay Deny.
3. **Do not rely on the `roles` claim or on Portal Settings.** Nothing reads the claim; Allow would add a portal role.
4. **Set a strong OAuth Client secret ourselves** (Data field, clear text in the identity database: treat the identity database as holding app credentials; backups are encrypted per Phase 1).
5. **The NXERP login page needs the SSO button** (6B) because it does not render Frappe's provider links.
6. **Server-to-server calls need a route to the identity site's public name** (Phase 5 edge aliases solve it on one host; in production the public https name works from the host).
7. **Lockout safety:** `disable_user_pass_login` refuses password POSTs for everyone including Administrator on that site; the break-glass way back is `bench console` (6D documents it).

## Not covered (UNVERIFIED)

Sessions over https (the `secure` flag) and a browser: the rehearsal used http and a scripted client; the human's browser check is GATE G6a. Revocation timing (what happens to an already open session when a user is disabled on the app site) is tested in 6C/Check 6.5, not here. Refresh tokens and logout propagation are out of scope.
